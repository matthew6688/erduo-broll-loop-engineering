# v1.0.1 稳定生产提速复盘

## 结论

本轮旧/新基准都保留五镜头 canary、4K 逐镜直出、完整解码、六格检查图、
文字审计、运动审计或真实看片。用户复看后确认新旧质量区别不大，可以
接受；新旧 35 秒 canary 的 SSIM 为 `0.999203`。

旧基线从视觉方案批准到技术门禁耗时 `79m37s`。新的独立生产根目录使用
同一原始 SRT、DesignMD、五个 canary shot、已批准可编辑源码和冻结素材，
但没有复制旧 MP4、检查图、合同、回执、审计或门禁；从新 Runtime Plan
写入到技术门禁耗时 `3m19s`，对应约 `95.8%` 的墙钟时间下降和约 `24x`
提升。实际命令累计约 `1m49s`：Lead 三镜约 `61s`，Builder 两镜约 `43s`，
机械回执与最终门禁约 `5s`。

这不是从零创作的等口径 24 倍加速。旧基线包含创意制作、返修和协调，
新基准复用了已批准源码。可被严格证明的是：稳定源码之后，五镜头机械
生产闭环已经从几十分钟级进入约两分钟命令时间、约三分钟完整墙钟时间。
新文稿从零创作的改善仍需下一条真实生产验证。

## 已实施改动

1. Runtime 规划前严格验证所有 `source: srt` 的可见文字；必须是原 SRT
   中的规范化原句。本次真实发现六条过期改写，错误不再进入渲染阶段。
2. HyperFrames Assignment Preflight 一次检查全部 composition，保留有界
   stdout 和 stderr，并把所有失败一起返回。
3. 确定性失败回执绑定源码 identity；源码未变化时禁止无意义地重复预检。
4. Lead/Builder 只返回看片结论。Parent 使用 `record-view-receipt.mjs`
   机械生成严格回执，避免创作角色手写证据。
5. Parent 使用 `finalize-canary.mjs` 重新打开并验证现有媒体、合同、六格图、
   审计、回执和 preview；看片后不再重复 Assignment 标准渲染命令。
6. `reuse-foundation-assets.mjs` 可以从已通过的 Assets gate 复用哈希一致的
   字体与 license；它不会复用截图、视频或其他单集素材。

## 经验教训

- 先区分创意时间、机器执行时间和人工看片等待，不能用一个总时长解释
  所有问题。
- 最昂贵的浪费不是高质量门禁，而是相同输入重复跑同一命令。应消除重复
  计算，不应删除检查。
- 能在规划阶段确定的错误必须在规划阶段关闭；错误越晚发现，返修成本越高。
- 失败输出必须完整且聚合。只显示 stderr 或逐镜失败，会导致修一个、跑一次
  的串行循环。
- 创意结论与机械证据应分离。创作角色负责看和判断，Parent 负责哈希、合同、
  回执和最终门禁。
- 性能基准必须明确复用了什么、没有复用什么。SSIM 和完整门禁用于证明提速
  没有悄悄改变画面或降低交付标准。
- 任何“更快”优化都必须先保留一个顺序执行基线，便于回退和比较。

## Claude 独立审查与决策

Claude 在无仓库访问、只读取 12 条事实的独立审查中，建议后续顺序为：

1. 自动记录 planning、preflight、render、review wait、receipt 和 finalization
   的结构化阶段耗时。这是低风险可观测性改动，也是后续优化的前提。
2. 在阶段计时完成后，实验性测试有界并行 preflight 或 direct-shot render。
   必须保留顺序模式，通过同一门禁、输出 SSIM 对比、资源受限复跑和两次
   render ceiling 断言后才能启用。
3. 区分确定性源码错误和极窄的 transient infrastructure failure。默认仍然
   fail closed；只有明确 allowlist 的 crash、timeout、OOM 或工具级 I/O 错误
   可以在源码不变时重试，并且必须留下不可变的 transient retry 记录。

实施结果：真实 planning、Lead/Builder、view receipt 与 finalization 命令会
自动写入闭合的结构化阶段事件；HyperFrames composition preflight 使用默认
上限 2 的隔离并发池，正式 render 仍保持顺序执行；失败分类保持
default-deny，只有进程信号、退出码 124/137 或明确的工具 I/O 错误进入
transient allowlist，并留下不可变回执。未知退出码仍绑定源码并禁止原样重试。

用户随后确认正式生产不需要 4K，因此新默认规格改为 1920×1080、30 fps；
4K 只有明确请求时才启用。这个选择降低机器成本，但没有删除 canary、完整
解码、检查图、文字/运动审计、真人看片或两次 render ceiling。上面的 SSIM
基准仍是同规格 4K 对比，不把分辨率变化冒充为既有测速收益。

## 下一次验证

下一条全新文稿应从零运行，并自动记录：Director、Assets、Lead authoring、
Assignment Preflight、逐镜 render/decode/sheet、实际看片等待、receipt、audit、
canary assembly 和 finalization。只有这次数据能回答“新视频从零生产到底提升
多少”，并决定安全并发是否真的值得启用。

三次机械复跑不直接复制正式 production root。新增的
`prepare-performance-sandbox.mjs` 只在 Runtime Plan、五镜 canary-first
Assignments、运行时 executable hash 和当前 Skill 输入全部有效时，选择性复制
原始输入、Director、Assets 与冻结可编辑源码，并生成指向隔离 sandbox 的命令
参数。它明确不复制 Visual Plan 批准、用户 canary 决定、view receipt、旧 MP4、
事件或 render-attempt ledger，因此 benchmark 不能冒充新的正式门禁进度。

真实旧 production root 的集成检查已按预期因 Skill hash 漂移而拒绝，并自动
清空目标 sandbox；这证明测速入口不会为复用旧源而绕过当前 Skill。正式正向
集成验证必须等待本轮新文稿在当前 Skill 下完成 Plan、Assets 与冻结 source，
随后才允许准备三次 sandbox，不得使用 legacy root 伪造成功证据。

## 2026-08-28 全新中文稿实测

五镜头冻结源的三次顺序机械基线为 `46.908s / 47.813s / 50.650s`，中位数
`47.813s`。15 组逐镜解码帧对比最低 SSIM `0.999655`，全部机械门禁通过。
这证明当前机器上的机械渲染不是分钟级瓶颈。

两个单变量候选都被隔离实验否决并回退：direct render 并发 2 的三次中位数
`52.695s`，比顺序基线慢 `10.2%` 且方差更高；合并 full decode 与六格图的
首轮为 `90.217s`，慢约 `88.7%`，达到停止条件后不再浪费两轮。正式渲染继续
保持顺序执行，既没有用并发数字冒充提速，也没有改画面或删除检查。

真实新稿的 Runtime Plan 成功路径只有 `27ms`，但 Lead 与 Builder 创意阶段
分别跨越 `18m22.654s` 和 `9m09.775s`，另有 `114–205s` 的观看/交接等待。
因此保留的改动只消除已重复发生的机械交接往返：Parent 生成 view receipt
时同时创建缺失的最小 handoff；已有 handoff 必须引用该 receipt，否则仍然
fail closed。此改动不触及 DesignMD、Recipe、源码、渲染、画质、人工观看或
用户批准。收益应按“每个已看片 Assignment 少一次角色重新唤醒”记录，不能
伪造为机械渲染百分比。

Claude 快速复审在本轮连续两次没有返回可用结果，故未把它写成支持证据；
实现决策来自上述本地三次基准、两项失败实验和真实 handoff 阻塞记录。
